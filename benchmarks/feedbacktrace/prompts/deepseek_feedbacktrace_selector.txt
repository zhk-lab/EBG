Apply these checks:

1. REAL HUMAN MESSAGE. Exclude system-generated or tool-generated targets such as task notifications, system reminders, automated monitor/Cron messages, tool output, interruption markers, command envelopes, and metadata. Use reason_code=system_injected_target.

2. PUSHBACK OR NON-PUSHBACK. Classify the target as correction, rejection, failure_report, requirement_change, takeover, or non_pushback. Mere position after Agent work is not enough. A pure acknowledgement, agreement, token/credential delivery, ordinary next request, or casual continuation is non_pushback.
   - If the Agent explicitly offered choices or an optional next action and the target only selects or authorizes one, classify it as non_pushback. Do not turn correct confirmation-seeking into a KEY.
   - If the Agent explicitly requested an error message, logs, a screenshot, a test result, or a diagnostic rerun and the target only supplies that requested evidence, classify it as non_pushback. This differs from a failed attempted fix: diagnostic instrumentation or information gathering alone was not represented as resolving the problem.

3. LINK TO A PRE-TARGET AGENT BEHAVIOR. A KEY must address a concrete observable Agent decision, implementation, tool action, validation choice, scope choice, claim, or refusal in Local. The evidence must establish what the Agent did or claimed; it does not need to establish that the later user-reported outcome is true.
   - For failure_report, the failure outcome may appear for the first time in the target. If the Agent previously implemented or claimed to fix the same component or problem, that prior behavior can ground the candidate.
   - A requested diagnostic return is a KEY only when it also demonstrates that an actual attempted fix or claimed resolution failed. When the Agent only added observability or asked for missing evidence and the target provides it, there is no corrected pre-target decision yet.
   - A target saying the result is still wrong, clarifying which behavior is wrong, or supplying new diagnostic details after an attempted fix is not automatically a new requirement.
   - Missing screenshots or attachments are fatal only when the remaining text cannot identify the relevant Agent behavior or the meaning of the feedback. If the text itself states the failure or correction, do not exclude merely because an image is unavailable.

4. CLEAR FIRST-TIME NEW REQUIREMENT. Exclude with reason_code=new_requirement only when the target introduces a feature, preference, constraint, or desired behavior that is genuinely unrelated to any earlier user goal and does not correct, reject, narrow, or respond to a concrete Agent choice. Treat same-task corrective clarification and follow-up failure after an attempted fix as eligible, even if the target contains details not stated earlier.

5. CONSEQUENTIAL ACTIONABILITY. A KEY should concern the task goal, constraint, implementation path, scope, validation, result meaning, evidence boundary, failure attribution, or user environment, and should plausibly merit must_disclose or worth_disclose. Exclude with reason_code=not_actionable only for a clearly low-impact typo, comment, formatting/naming issue, routine mechanical error with no meaningful decision, or an action already explicitly authorized. Do not use not_actionable merely because a reported failure is objectively repairable; an inadequate fix, validation claim, or implementation choice can still be consequential.

6. DIRECT GROUNDING. For KEY, return one or two Local Agent evidence IDs that directly identify the Agent behavior under review. Ground the behavior, not the target's later observation. An omission-based KEY still requires an Agent event explicitly showing a skip, refusal, scope exclusion, or intentional omission; absence alone is not selectable evidence.

7. EXCLUSION THRESHOLD. Exclude when a failure above is clear: system-generated target, clear non-pushback incompatible with a KEY candidate, clear unrelated new requirement, clear non-actionability, no identifiable pre-target Agent behavior, indispensable missing context, or otherwise invalid context. Do not use ambiguous as a convenient rejection reason. If a concrete Agent behavior supports a reasonable KEY reading, pass it forward.
