# EBG：Evidence-Grounded Behavior Graph

## 1. 方法目标

EBG 以确定性规则将代码仓库或执行轨迹中的分散证据组织为行为证据图，支持模型对长程 Agent 的行为进行分析与问题定位。

EBG 面向长程 Agent 的行为分析与问题定位，针对长上下文中证据分散、关键线索易被淹没，以及任务要求与行为证据难以对照的问题，通过结构化行为图关联证据，通过任务导向的读取与呈现突出相关依据，帮助监督模型理解行为、排查问题并准确定位。

EBG 围绕两个核心问题展开设计与验证：

1. **结构化的行为图是否有助于模型定位和理解证据？** 通过 Behavior 组织局部证据、Scope 保留共享上下文、显式关系边连接可确认的跨位置联系，检验行为图组织的价值。
2. **任务导向的读取与呈现是否进一步帮助模型排查问题？** 通过任务相关的入口选择，以及任务要求与证据的对齐呈现，检验模型如何利用行为图完成具体任务。

两者形成递进关系：先验证证据如何组织，再验证这些证据如何面向任务使用。

             Agent Context
             /           \
      Workspace       Execution History
        (Repo)             (Trace)
             \           /
          确定性提取与组织
                  ↓
     Evidence-Grounded Behavior Graph
       原始证据 · 行为单元 · 关系
                  ↓
           面向模型的证据呈现
             /           \
      Repo 局部图      Trace 任务图
             \           /
              模型监督
          行为分析 · 问题定位

思路：正文讲统一框架及其必要性，附录讲两类输入的具体实现。

每个模块的正文按同一逻辑展开：
1. 核心：用一两句话说明这个模块做什么。
2. 为什么需要：上一层表示还缺少什么，为什么需要这一层。
3. 如何定义：明确新引入的概念，以及它如何解决上述问题。
4. 有什么作用：说明输出如何支撑后续模块和最终判断。

## 2. 模块一：Evidence Extraction

### 正文材料

**核心。** Evidence Extraction 将 Agent 的工作上下文转换为统一的证据单元，保留原始内容与来源位置，为行为建模提供可引用的基础。

Agent 的工作上下文由形式不同、分散存放的材料组成。后续分析不仅需要读取这些内容，还需要明确每项判断引用了什么、依据来自哪里。因此，EBG 将 Evidence 定义为从可见上下文中提取、保留原文并可独立定位的证据单元，以统一方式记录其内容、来源类型和位置。

提取过程依据输入结构采用确定性规则：代码侧保留代码片段，轨迹侧保留交互单元。两类证据遵循相同的原文保留与来源定位原则，不在提取阶段生成摘要或问题判断；具体划分规则见附录 A。

Evidence 为后续行为构建和关系建立提供共同的引用基础。同一条证据可以被多个行为引用，其原文与位置始终保留，使模型能够核对判断依据，并将发现的问题定位到具体输入。

### 附录论文材料 A：Evidence 提取规则

Evidence Extraction 首先限定可使用的输入范围，再依据材料结构划分证据单元，最后统一记录内容及来源位置。以下规则确定后续行为构建所能引用的原始材料，不在提取阶段生成摘要、问题标签或正确性判断。

#### A.1 输入边界

代码仓库侧仅提取生产源码、可执行脚本、运行时模板和行为配置。普通文档、测试、CI、构建产物及第三方目录不进入行为图。任务文档独立保留，作为模型判断的语义基准，不生成 Evidence 或图节点。在本文评测中，SpecGap 使用完整的 `document_after`，SilentSwap 使用完整的 `original_document`；后续模块利用文档中的路径、Symbol、调用名和配置键匹配代码图。

执行轨迹侧保留截止点前可见的用户消息、Assistant 回复、工具交互及前置系统消息。失败调用、重复尝试和后续修正均参与提取，以保留实际执行过程。不读取 Gold、patch、修改前代码或截止点后的事件；截止点前发起、截止点后才返回的调用仅保留可见的调用部分。

#### A.2 按材料结构划分证据

代码材料按语法或配置结构划分，执行轨迹按交互单元划分。提取粒度以保留相应单元的完整内容为原则，不要求每条 Evidence 都是最小事实片段。

**代码仓库。** 不同材料采用以下规则：

| 材料类型 | 提取单位与规则 |
|---|---|
| Python 源码 | 基于 AST 提取函数或类的定义头、控制结构头及普通语句；主体递归提取，不再重复保存整个复合结构；多行头部和多行语句完整保留。 |
| 非 Python 源码与可执行脚本 | 完整文件作为一条 Evidence，作用域记为 `<module>`。 |
| 行为配置 | 按可识别的配置项提取；无法识别时保留完整文件。 |
| 运行时模板 | 按非空原文行提取，并记录所在的 `block` 或 `macro`。 |

Python 的普通语句包括赋值、导入、返回、异常抛出和独立调用等。语句内部的表达式不额外拆分，例如 `return f(x)` 保留为一条返回语句，不再为 `f(x)` 生成重复片段。同一来源位置的片段仅保存一次，允许多个 Behavior 引用。提取时不主动扩展为整个函数，连续函数上下文由后续模块通过 `path + symbol` 获取。

**执行轨迹。** 一次工具调用及其对应结果构成一条工具 Evidence；每条 Assistant 回复、用户消息和前置系统消息分别构成独立的 Evidence。Assistant 消息若同时包含回复文本和结构化工具调用，两者按原有字段分别归入回复 Evidence 和工具 Evidence，不重复保存调用内容。

调用与结果依据原始调用标识或输入中已有的明确配对关系合并，不凭相邻位置或工具名称推测配对。输入已提供完整 `tool_exchange` 时，直接保留该交互单元。并行调用分别形成 Evidence；同一调用对应多个结果片段时，全部保留并维持原始顺序。缺少结果的调用或无法匹配调用的结果均单独保留，不补造缺失内容，不丢弃可见事件。

#### A.3 证据记录与定位

每条 Evidence 保存四项信息：编号（`evidence_id`）、来源类型（`source_type`）、原文（`content`）和原文位置（`locator`），使后续判断能够找到对应依据。

- **代码片段**：记录文件路径、所在函数或其他作用域，以及起止行号；顶层代码的作用域记为 `<module>`。
- **轨迹消息**：记录轮次、事件序号、消息类型和原始证据 ID；没有原始 ID 时留空。
- **工具交互**：记录工具名称和调用标识（如有），分别保存调用与结果的原文及位置，即使两者不相邻也能准确定位。

所有内容保持原文。轨迹证据按首次出现的位置排列，并保留内部各片段的位置，以恢复原始事件顺序。编号由来源和位置固定生成，相同输入得到相同证据和顺序。


## 3. 模块二：Behavior Construction

### 正文材料

**核心。** Behavior Construction 将相关 Evidence 组织为具有内部结构的行为单元，为模型理解行为及其相互关系提供统一的表示。

单条证据通常只能呈现行为的一个局部，模型仍需自行寻找并关联其他证据，才能理解行为发生的背景、执行内容及其结果。EBG 因此引入 Behavior，将其定义为围绕同一行为组织的证据集合，并明确各条证据在其中承担的作用。Behavior 通过结构化关联表达行为含义，各部分均保留原始 Evidence 引用。

这一表示同时适用于代码与执行轨迹：代码侧以“条件—操作—结果”组织证据，轨迹侧以“需求—行动—回复”组织证据。两者共享“以行为为单位关联证据”的构建原则，具体划分和匹配规则在后续实现材料中说明。

Behavior 将原本分散的证据组织为可共同阅读和分析的单元，减少模型自行拼接上下文的负担，并为后续跨行为关系建立与证据呈现提供基础。构建过程采用确定性规则，不预判行为是否正确；模型结合任务要求作出判断，并可通过证据引用回到原文核对。

### 附录论文材料 B：行为单元构建规则

#### B.1 行为单元的定义

Behavior 将共同描述一个局部行为的 Evidence 组织在一起，并明确各项证据在其中承担的角色。构建的关键是确定哪些证据应当共同理解，以及何时需要将它们划分为不同的行为。EBG 根据材料中可观察的结构和对应关系确定这些边界，使行为表示保留原始依据，而不依赖生成式摘要。

代码与执行轨迹提供了不同的行为线索。代码通过条件、操作及结果描述可能发生的行为，因此以可观察结果为锚点组织证据；执行轨迹记录需求、实际行动与回复，因此以需求及其履行过程组织证据。两者都保留 Evidence 引用，允许不同的行为共享同一原始证据，并将行为是否符合任务要求留给后续分析。

#### B.2 代码行为：关联结果、条件与操作

对于代码仓库，一个 Behavior 表示同一作用域内、围绕一个可观察结果组织的一条控制路径。返回、异常抛出、状态更新以及可识别的输出或外部操作提供结果锚点；函数、方法等语法作用域限定证据的组合范围，避免将不同位置的条件与结果错误拼接。

围绕结果锚点，构建过程关联两类证据：一类是控制结果发生的条件，另一类是产生结果所需的操作与数据来源。前者依据分支结构确定，后者依据结果及条件中使用的变量与其定义关系确定。例如，某个返回值由前面的计算产生，该计算便与返回语句共同组成行为；仅在位置上相邻、却不参与结果或条件形成的语句，不因此被纳入。

| 构建判断 | 可观察依据 | 组织方式 |
|---|---|---|
| 结果在哪里 | 明确的返回、异常、状态写入、输出或外部操作位置 | 以该位置作为行为锚点 |
| 在什么条件下发生 | 包围结果及相关定义的条件与分支结构 | 将对应控制证据与结果关联 |
| 结果由什么产生 | 变量使用、赋值与数据来源之间的明确联系 | 纳入相关操作证据 |
| 是否属于不同路径 | 同一控制结构下互斥的分支 | 分别构建行为，允许共享原始证据 |

不同条件路径分别组织，即使它们最终到达同一结果位置，也保留各自的条件与操作组合。例如，同一函数根据不同分支选择数据来源后返回结果，两条路径可以共享返回语句，但不能将互斥的数据来源合并为一次行为。这里表示的是代码中可辨认的控制路径，不等同于已经发生的执行过程。

每个代码行为必须具有结果证据；条件或操作可以为空。无法从材料中明确识别的结果或数据来源不被补造。构建出的行为保留作用域与原始位置，为模块三建立跨位置联系提供基础。

#### B.3 轨迹行为：对应需求、行动与回复

对于执行轨迹，一个 Behavior 表示一项可辨认的需求及其履行过程。需求来自用户消息，行动来自工具调用及其结果，回复来自 Assistant 的解释、决定或结果汇报。按来源区分这三类角色，使实际执行的内容与向用户声称的内容能够共同呈现并接受对照。

构建首先以用户消息及随后发生的工具交互和回复为候选范围，再根据需求与事件的对应关系确定是否拆分。用户消息中的最外层编号、同级条目和独立问句提供候选需求边界；嵌套说明仍属于上级要求。条目边界本身不足以决定行为边界，还需要后续行动或回复提供对应依据。

| 构建判断 | 可观察依据 | 组织方式 |
|---|---|---|
| 是否包含独立需求 | 最外层编号、同级条目、独立问句 | 形成候选需求片段 |
| 行动对应哪项需求 | 工具或命令表达的操作类型，以及明确的路径、测试名、运行标识等对象 | 优先通过对象对应关联需求与行动，结合操作线索区分候选 |
| 回复对应哪项需求 | 回复中出现的对象、操作或具体结果名称 | 关联相应回复，保留其声称的原文 |
| 是否可以拆成多个行为 | 各项需求与行动、回复之间可区分的对应关系 | 对应明确时拆分，否则保留复合行为 |

例如，“修改某文件”可以通过修改操作及相同文件路径与后续工具事件对应，“验证某项测试”可以通过测试命令和测试名称与执行结果对应。对象未完整重复时，可结合操作类型和明确的名称片段辅助匹配；只有通用的“完成了”或主题相似，不能为独立拆分提供充分依据。

同一需求下的读取、修改、验证及失败重试可以共同组成行动证据，保留其执行顺序。若多个需求共享一个无法区分的操作结果，则保留复合行为，避免割裂履行过程。一条回复明确回应多个需求时，可以被多个行为引用；需求片段和回复内容均保留原文对应关系。缺少行动或回复时，相应角色可以为空；只有用户需求而没有后续行动与回复的事件不单独构成行为。



## 4. 模块三：Behavioral Graph Construction

### 正文材料

**核心。** Behavioral Graph Construction 通过行为作用域（Behavioral Scope）与显式关系边两种互补的方式组织行为结构，保留共享上下文及具有明确证据支持的联系，形成统一的行为证据图。

Behavior 组织了单个行为内部的证据，但理解与检查一个行为，往往还需要对照其他行为。行为之间既有共享上下文中的分支、承接、重试与修正，也有能够直接定位的调用、数据传递与引用。前一类联系具有丰富的语义，需要结合上下文理解；后一类联系具有清晰的可观察信号，适合明确标注。因此，EBG 同时采用作用域组织与显式连接来表达这些结构。

**行为作用域。** Behavioral Scope 通过包含关系和原始顺序组织需要共同理解的行为。代码侧以 Symbol 界定作用域，保留行为所在的源码位置与分支结构；轨迹侧以 Task 界定作用域，保留任务内的行为归属与事件顺序。Scope 将这些行为及其原始依据置于共同上下文中，使其中丰富的语义联系可供模型分析，而无需预先将其逐一标注为固定类型的关系边。源码顺序与事件顺序分别保留，不将代码排列等同于实际执行顺序。

**显式关系边。** 对于具有清晰证据信号的联系，EBG 采用确定性规则记录其端点、方向、类型及支撑 Evidence。代码侧包括作用域之间的调用与数据传递，轨迹侧包括任务之间的显式引用与首次出现顺序。显式边为模型提供可直接追溯的结构联系，与 Scope 所保留的上下文结构共同支撑跨位置分析；具体构建规则见下方附录材料。

本模块输出同时包含作用域归属与显式关系的行为证据图，为后续任务导向的读取与呈现提供结构依据。Behavior 保留原始 Evidence 引用，Scope 保留共同理解所需的上下文，显式边保留可确认的连接。模型据此对照相关证据、理解行为联系，并将判断定位到具体原文。

### 附录论文材料 C：行为图构建规则

#### C.1 两种互补的结构表达

行为图通过 Behavioral Scope 与显式关系边组织局部行为。Scope 表达行为的共同归属，并保留其原始位置和顺序；显式边表达能够由证据明确确认的特定联系。两种结构分别支持上下文中的行为对照与跨位置的证据关联。

Scope 内部可以包含分支、承接、重试或修正等多样的语义联系。构建过程保留理解这些联系所需的原始上下文，不将它们预先枚举为行为之间的两两关系。对于具有明确调用、数据使用或引用信号的联系，则直接记录关系类型与依据。所有 Behavior 均保留原始 Evidence 引用，使这两种结构能够回到具体内容核对。

#### C.2 Behavioral Scope：组织共同上下文

**代码作用域。** Repo 以 Symbol 界定 Scope，将同一函数、方法或其他代码作用域中的 Behavior 组织在一起。作用域边界由代码的语法结构确定，文件路径与限定名称共同区分不同位置。Scope 保留所属行为、源码位置及连续源码上下文，其中的条件与分支结构仍由原文表达。

同一 Scope 可以包含多个结果或多条互斥路径。共同归属使这些行为能够被放在一起检查，但不表示它们必然依次执行。例如，同一函数中的两个返回分支属于同一 Scope，其先后位置反映源码排列，具体执行条件仍需结合分支证据理解。

**任务作用域。** Trace 以输入中可确认的结构关联界定 Task Scope，将具有共同任务归属的 Behavior 组织在一起。这里的 Task 是由交互结构确定的任务单元，其范围由显式归属信息决定，不要求覆盖语义上完整的持续工作。局部行为构建后，通过其原始事件携带的任务标识、回复指向与执行标识确定作用域。

| 结构信号 | 归属规则 |
|---|---|
| 显式任务标识 | 输入提供具有任务归属含义的 task ID 时，将同一标识下的行为归入同一 Scope；不同任务标识保持分离 |
| 明确回复指向 | 输入提供指向具体请求的回复指针，且该指针表示当前请求的应答关系时，将回复关联到该请求所属的 Scope |
| 执行标识 | 调用、结果及后续状态事件通过同一 run/job ID 关联，且该次执行具有唯一任务归属时，将相关行为归入该 Scope |

这些标识和指向必须由输入结构明确提供。正文中提到同一编号、文件或先前结果，仅表示内容引用，不能直接作为共同任务归属；回复指针若只表示引用或评论对象，也不用于合并任务。执行标识首先确定同一次执行，只有能够关联到唯一任务时，才进一步确定任务归属。

#### C.3 显式关系边：连接可确认的联系

显式边连接 Scope，并通过支撑 Evidence 定位到具体行为或原文位置。关系成立需要明确的结构信号；仅有主题相似、位置相邻或可能的语义关联，不足以建立调用、数据传递或引用关系。

| 关系 | 支持信号 | 方向与含义 |
|---|---|---|
| Repo：`calls` | 代码中可唯一解析的直接调用 | 调用方 → 被调用方，表示直接调用联系 |
| Repo：`feeds` | 明确的返回值、模板产出或状态写入被另一作用域使用 | 生产方 → 使用方，表示可定位的数据传递 |
| Trace：`references` | 后续任务明确引用先前任务中的对象、原文或条目 | 引用任务 → 来源任务，表示对先前内容的明确引用 |
| Trace：`precedes` | 不同任务首次出现的原始事件位置 | 较早任务 → 较晚任务，只表示首次出现顺序 |

**代码关系。** 调用边要求能够确定目标作用域，数据传递边要求能够识别产出及其使用位置。二者保留原始支撑证据，不从无法解析的动态调用、歧义目标或间接关系推断新边。边的端点采用代码作用域，具体涉及哪个 Behavior 可由支撑 Evidence 与行为引用对应。

**任务引用。** EBG 通过显式引用锚点连接引用位置与来源内容。当锚点能够唯一定位到先前另一任务中的证据时，建立由引用任务指向来源任务的 `references` 边。

- **对象锚点：** 请求或工具参数中的对象标识、提交编号或产物链接，对应先前任务的输出。
- **引文锚点：** 引号或引用块中的完整原文，对应先前回复中的片段。
- **条目锚点：** 明确的条目标签，对应前一轮回复中的唯一列表项或表格行。

每条边保留引用与来源两处 Evidence。匹配限定在 Behavior 所引用的原文范围内，依据标识一致、原文对应或条目定位完成；仅统一书写格式，不采用语义近似。来源不唯一或只有内容重复时不建边，同一任务内的引用保留在 Scope 中。引用关系表示内容指向，不推断因果、依赖或对象创建关系。

**任务顺序。** 首次出现顺序边仅连接相邻的任务；同一事件中首次出现的任务视为并列，不强行排序。任务恢复不新增此类边，例如 A、B、A 只产生 A 到 B 的首次出现顺序边，后续交错由事件位置保留。这种关系不表示完成顺序、因果或依赖，也不用于推断答案所在任务。

相同端点与类型的关系合并其支撑证据。所有关系均保留原始依据，并按确定顺序组织；来源或目标无法可靠确定时，不生成该关系。

#### C.4 两种结构如何支持行为对照

以缓存读取函数为例，命中缓存与未命中缓存的分支分别形成 Behavior，由同一 Symbol Scope 保留共同上下文。模型可以据此对照两条路径的条件、操作与返回结果；若未命中分支调用另一函数获取数据，则调用边进一步连接该函数的 Scope，支持追踪局部行为之外的实现依据。Scope 保留内部对照所需的上下文，显式边提供跨作用域的明确联系。

在执行轨迹中，多次尝试、失败反馈与后续回复可以共同归入一个 Task Scope。模型根据原始内容和事件顺序检查其履行过程，构图阶段无需预先标注哪些行为构成“修正”。若另一任务明确引用该任务中的产物或结论，则通过引用边连接两者。共同归属与明确引用分别表达不同层次的联系，不以同属一个 Scope 代替特定关系的证据。

#### C.5 图的输出与表示边界

行为图保留四类信息：原始 Evidence 及来源位置、Behavior 的内部证据引用、Scope 归属与上下文、显式关系及其支撑证据。Repo 通过文件路径与 Symbol 表达归属，Trace 通过任务标识表达归属；Scope 是图中的组织结构，无需另行生成重复的摘要节点。源码顺序与事件顺序分别保留，不统一解释为执行顺序。

输出检查确保行为与关系的引用存在、作用域归属和原始位置一致、关系端点有效，并使相同输入产生相同结构。同一原始证据可以被多处引用，但不因此改写或重复构造事实。图中不包含标准答案、模型候选结论或预先判定的问题标签。

构建图与呈现图分别承担不同职责。本模块保留行为结构，模块四决定如何根据任务选择与展示这些结构。当前 Trace 呈现保留任务引用边的类型与目标任务，首次出现顺序边不展示；内部关系的完整依据仍保存在图中。局部读取、邻居展开及具体呈现格式由模块四说明。



## 5. 模块四：Task-oriented Evidence Presentation

### 通俗理解

模块三已经把代码及其行为关系画成了一张完整地图。模块四根据当前任务，决定照亮地图上的哪些地方，让模型集中阅读这些地方的原文以及它们之间的联系。

首先，根据任务文档给文件目录排序，帮助模型找到更可能包含相关证据的文件。选中文件后，再沿着文档提到的函数、调用名等线索，点亮文件中对应的作用域。这些最先被点亮的位置，就是“种子节点”。

接着，从每个种子沿已有关系向外照亮全部一跳邻居，不限制边数。例如，一个函数调用了另一个函数，就可以把被调用函数的相关内容也照亮。这相当于为文档直接指向的位置补上周围的上下文；照亮范围只从预先选好的种子扩展一层，不会不断向外蔓延。

不同种子照亮的区域可能接到一起：两个种子可能通过选中的边直接相连，也可能照亮同一个邻居。接上的部分就连成一片，形成一块连通子图；没有接上的部分则各自保留。最终，地图上会出现一片或几片相连的区域，模型可以把每片区域中的相关行为放在一起理解。

最后，每片区域从连接不同邻居最多的种子开始展示，这个展示起点就是 Root；并列时，选择在文档中最先被明确提到的种子。种子决定最初点亮哪些位置，每片区域只选一个 Root 决定从哪里开始读。模型看到的是这些区域中的原文、位置和关系；其他内容仍在大图里，只是这次没有展示出来，后续仍可继续查找。这样便能减少与当前任务关联较弱的输入，同时保留所选证据之间的联系。

对于执行轨迹 Trace，重点是把多轮交互中分散的内容按任务整理好：将同一任务的需求、实际行动和回复放在一起，标出当前任务与历史任务，完整保留证据，方便模型核对“要求做什么、实际做了什么、最后说了什么”。

### 正文材料

**核心优势。** 面对分散在多个文件和作用域中的证据，模型既难以找到应读的位置，也难以从零散片段中还原行为之间的联系。Task-oriented Evidence Presentation 通过任务导向的目录排序帮助模型优先找到相关文件，再将文档匹配的作用域及其直接关联证据组织为连通子图，减少逐处查找和拼接上下文的负担，使模型在有限阅读预算内能够结合相关行为及原始依据进行判断。

#### 4.1 任务导向的目录排序

根据任务文档中的文件路径、Symbol、调用名和配置键等明确线索排序文件目录，并提供可读取标识及文档对应提示，帮助模型优先选择相关文件。目标是提高包含 Gold KEY 必要证据的文件被选中的机会；排序只使用任务文档和可见仓库信息，不使用 Gold，也不将相关性解释为存在问题。未进入初始展示目录的文件仍可通过搜索访问。

#### 4.2 文档引导的种子顶点选择与邻域展开

文件选择确定了候选范围，但文件内仍混合着服务于不同功能的内容。EBG 利用文档中的符号引用、调用名和代码标识符，将所选文件内所有能直接对应的 Scope 纳入种子集合，不按排名或数量截断。每个 Scope 由文件路径与 Symbol 标识，将文档线索落到具体实现位置。

从种子顶点出发，沿有证据支持的调用与数据传递关系向外扩展，为文档直接指向的位置补充理解其行为所需的邻域上下文。每个种子保留全部一跳关系及对应邻居，允许跨文件访问，不限制边数；新增邻居不递归展开。各邻域的顶点与边合并后，形成原始静态图中面向当前任务的局部子图，并保留入选关系的方向、类型及支撑证据。

这种“种子顶点选择—邻域展开”的方式，使模型的阅读范围集中于文档相关位置及其直接联系，旨在减少整文件输入中与当前任务关联较弱的内容及其 token 开销。

#### 4.3 连通子图组织与阅读起点

不同种子的展开结果可通过共享顶点或入选关系相互连接，使原本分散的种子及其邻域连成同一块子图；未相连的部分则各自保留，最终形成一个或多个连通子图。EBG 以这些子图为单位组织证据，使模型能够共同阅读相互关联的行为及其上下文。连通性按忽略边方向后的弱连通分量确定，展示时保留关系的原始方向和类型。

为使连通子图具有清晰的阅读顺序，EBG 在每个连通分量的种子中，选择连接不同邻居最多的一个作为 Root，即该子图的展示起点；并列时按种子在文档中首次被明确提到的顺序选择。邻居数仅在已选子图内统计，其他种子仍完整保留，Root 的选择不改变证据范围，也不表示程序执行或因果起点。

#### 4.4 Trace 的任务导向呈现

执行轨迹中的需求、行动和回复往往分散在多轮交互中，同一任务也可能被其他任务打断。EBG 完整呈现轨迹证据，以 Task Scope 汇集同一任务下的 Behavior，在行为内部共同展示需求、实际行动与回复，并保留原文、事件位置和任务间的明确引用关系。这种组织方式帮助模型将分散的执行过程与相应要求对照，减少跨轮次查找上下文的负担，为判断任务履行情况及需要披露的决定提供依据。



### 附录论文材料 D：任务导向的读取与呈现

#### D.1 设计目标

行为图保留了证据之间的结构联系，但模型仍需找到与当前任务相关的位置，并从分散内容中恢复行为上下文。Repo 通过目录排序引导文件选择，再以文档匹配的种子顶点和全部一跳邻域选取局部证据，按连通子图组织阅读。Trace 则完整保留任务证据，通过任务归组和需求、行动、回复的共同呈现支持跨轮次对照。

两类呈现均利用已有的 Behavior、Scope 与显式关系，保留原文及来源位置，帮助模型联合使用相关证据。Repo 的局部选择旨在减少与当前任务关联较弱的输入，Trace 的任务组织旨在减少跨轮次查找与对照的负担；证据覆盖、判断效果与 token 成本分别评估，不将输入缩短直接视为效果提升。

#### D.2 任务导向的入口选择

代码仓库中的证据分布在多个文件与作用域中。EBG 从任务文档的明确引用出发，将要求对应到可读取的位置，再利用图结构提供相关入口。

| 入口依据 | 选择方式 |
|---|---|
| 文档明确给出的文件路径、限定 Symbol、调用名或配置键 | 对应到可确定的代码位置，优先作为直接入口 |
| 与直接入口相连的调用或数据传递关系 | 作为相关入口，支持进一步检查跨位置证据 |
| 多个文档章节分别对应不同位置 | 在初始目录中兼顾各章节的入口，避免单一章节占满阅读预算 |

初始目录提供文件、可读取标识及文档对应提示，帮助模型决定从哪里开始。入口排序表示与任务的关联，不表示代码存在问题；没有进入初始目录的位置仍保留在查询范围内，可以继续搜索和读取。

文件选定后，文档中的明确引用进一步对应到文件内的 Scope，所有直接对应的 Scope 均纳入种子集合；缺少直接对应时，以固定的代表作用域提供备用种子。种子用于确定邻域选择的位置，不预先等同于最终 Root。每个种子独立沿模块三已有且有证据支持的关系展开全部一跳邻居，不限制边数，允许跨文件访问。新发现的邻居不加入种子集合，因此不会触发递归展开。

Trace 采用完整输入，不进行目录排序或入口检索。其任务导向设计主要体现在任务状态标记及需求与行为证据的共同呈现。

#### D.3 任务与证据的对齐呈现

**代码侧。** 不同种子的邻域通过共享顶点或入选关系相互连接，形成一个或多个弱连通分量。EBG 以这些连通子图为阅读单元，统一展示节点内容与关系，保留孤立种子，不为连接分量额外补边。对于文档明确引用的 Symbol，在对应源码旁提供文档章节与名称提示；通过关系补充的源码则附带调用或数据传递关系及其位置，使模型能够辨认任务依据与关联上下文。

Root 在子图形成后确定，每个连通分量选择不同邻居数最多的种子作为唯一展示起点。统计限于已选子图，忽略边方向、合并重复邻居并排除自环；并列时优先选择文档中首次明确提及位置靠前的种子，仍并列或没有文档对应时按文件路径与 Symbol 排序。孤立种子以自身为 Root。展示从 Root 开始，将节点原文与关联关系一起呈现，允许沿入边或出边访问其余节点，但始终标明关系的真实方向和类型；已展示节点通过引用连接，避免共享节点和循环造成原文重复。展示遍历仅访问已选子图，不触发新的邻域扩展，也不将图改成树。

Repo 的对齐形式是“完整任务文档 + 局部文档锚点 + 对应源码”。局部锚点提供要求所在位置的提示，不在每个阅读单元中重复完整要求原文，也不生成新的要求摘要。只有明确的文档对应才显示锚点，普通检索命中不被表述为直接文档依据。

这种呈现使任务依据、实现证据及关联上下文具有可辨认的对应关系。源码始终保留文件路径和行号，模型需要依据实际读取的原文判断，不能仅根据目录或文档锚点得出结论。

**轨迹侧。** Trace 按已有 Task Scope 展示 Behavior，并在每个行为内展开相应的需求、工具交互与 Assistant 回复。需求片段与执行证据共同出现，使模型可以直接核对“要求做什么、实际做了什么、向用户报告了什么”。这些对应关系由前序模块构建，本模块负责将引用展开为可共同阅读的原文。

当前任务由截止点前最后一个 Behavior 的任务归属标记，其余任务保留为历史上下文。该标记反映截止点处的处理位置，不表示问题一定出现在当前任务。所有 Scope 均保留；任务引用以简短的关系类型与目标任务呈现，首次出现顺序边不单独展示，原始顺序仍由事件位置与行为排列保留。

#### D.4 证据范围与呈现原则

读取内容需要同时保留局部证据的精确位置与理解行为所需的上下文。Repo 通常保留种子的连续作用域源码，模块级种子可采用与文档匹配的证据片段；邻居的关系依据能够定位到具体 Behavior 时，呈现对应行为的源码，不能可靠区分时保留完整作用域。内容范围由种子与邻域选择决定，不因节点最终成为 Root 或内部节点而再次裁剪。一跳展开规则与读取预算作为实验参数记录；预算仅限制单次展示量，尚未展示的节点与关系通过分页继续读取，不视为已被模型阅读或已被判定为不重要。

呈现遵循以下原则：

- **依据可定位。** 保留原文、代码行号或事件证据标识，使最终判断能够引用具体来源。
- **角色可区分。** 区分文档匹配种子、备用种子与关联邻居，单独标识阅读起点 Root；轨迹中区分需求、行动与回复。
- **上下文可理解。** 保留所选行为的条件与操作；范围无法可靠缩小时，采用完整作用域。
- **内容可继续访问。** 同一次读取中的重复源码合并展示，未选中的其他位置仍可另行读取。

Trace 完整呈现已有 Scope 中的行为及其对应证据，不通过任务筛选或摘要缩短历史。所展示的需求与回复片段保持逐字内容，引用仍可回到原始 Evidence。

#### D.5 从任务到判断的示例

假设任务文档先提到 `Client.run`，再提到 `Client.flush`，二者位于同一选中文件，并都调用 `emit`。两个文档匹配的作用域成为种子；若各自的一跳选择均保留该调用边，其邻域便通过共享的 `emit` 连接，形成 `Client.run → emit ← Client.flush` 这一弱连通子图。两个种子各有一个邻居，因此按文档顺序选择 `Client.run` 作为 Root；`emit` 虽有两个邻居，但不是种子，不参与 Root 选择。展示从 `Client.run` 开始，经 `emit` 访问 `Client.flush`，保留后者调用 `emit` 的真实方向；每个节点的原文只展示一次。

在这个过程中，文档线索引导文件与种子选择，入选关系使分散邻域连接，种子的邻居数与文档顺序共同确定展示起点。文档锚点、源码及关系依据共同保留要求与实现的对应线索；是否存在错误、哪些决定需要披露，仍由模型结合完整任务文档和实际读取的证据判断。

Repo 通过搜索、读取和提交三个动作完成这一过程：搜索定位入口，读取取得原始依据，提交给出判断及引用。Trace 则一次性提供完整任务视图后完成分析。模型配置、公平比较条件、具体预算和重试策略属于实验与复现设置；交互方式见第 6 节实验协议，比较条件与参数见第 7 节实验配置。






## 6. 实验协议

我们采用两种受控交互协议，模拟长程 Agent 工作中的环境取证与执行回顾。在本文的代码工作场景中，Repo 是 Agent 的工作环境，保存代码及其行为逻辑；Trace 是 Agent 的执行历史，记录用户要求、工具操作与结果汇报。因此，分别使用 AgentLoop 与 TraceReview，从工作环境和执行过程两个角度评估模型分析行为、排查问题的能力。

### 6.1 AgentLoop：Repo 交互式取证

AgentLoop 提供三个动作接口：`search` 搜索相关代码入口，`read` 读取证据，`finish` 提交问题判断及对应代码位置。模型获得任务文档和代码目录后，每轮选择一个动作，逐步取证直至提交。`read` 在 Raw 中返回原始文件，在 EBG 中返回任务相关的局部行为图证据。该过程模拟模型进入工作环境、查找实现并依据任务要求检查问题的取证过程。

### 6.2 TraceReview：Trace 轨迹分析

模型一次性读取截止点前的执行记录，对照用户要求、实际行动与结果汇报，找出需要核查的问题并指出支撑证据。Raw 提供原始轨迹，EBG 提供按任务组织的行为证据。该过程模拟对长程执行历史的回顾与检查。
