**整体流程与触发条件**

本文定义 autoresearch 审查流程。Hook、session 状态及四个 Skill 已按此实现；Plan 意图的自动识别覆盖明确执行请求，未识别的情况由 Codex 主动发起检查。模型是否充分取证、正确判断及及时提问仍需实际会话验证。

**以 session（一次对话）为单位**：新开对话建立独立的统计和检查状态；同一对话内追加 Prompt、继续执行或恢复对话不重置，记录不跨 session 混用。

```text
Hook 持续记录会话、工具执行和代码状态
        ↓
① 准备执行 Plan → 读取该 Plan 后，由 PostToolUse 提醒检查
   目标与计划澄清 → ebg_review(ambiguity)
   核对关键要求与必要假设；无歧义也记录检查结论
        ↓
执行过程中记录失败与重要调整，不因每次失败或验证结束立即审查
授权内的调整 → 当时记录，继续执行
需要用户决定且已有授权未覆盖的取舍 → 落实前核对、反馈并等待答复
        ↓
② Stop（准备结束本轮回答）→ 待澄清则放行提问；否则分别判断两类条件
   工具失败／关键歧义／重要调整 → ebg_review(adjustment)
   执行过 Plan／调用或耗时达阈值／结果限制 → ebg_review(result)
   两类都满足 → 先 adjustment，后 result；均不满足 → 直接回复
        ↓
每项审查必须调用 ebg_evidence 核实相关材料，再形成判断
        ↓
ebg_record 保存判断、依据及处理情况
        ↓
随结果披露重要调整和仍影响结论的限制；无重要问题则正常汇报
```

**三个审查阶段、两个触发时点**

| 阶段 | 触发条件 | 检查内容 |
|---|---|---|
| **目标与计划澄清（ambiguity）** | 仅执行 Plan 的任务触发：读取该 Plan 后提醒，材料足够时、执行前完成；普通 Prompt 或仅阅读讨论 Plan 不触发 | 目标、范围和验收是否明确，是否存在影响实现或结果解释的关键歧义与假设 |
| **执行调整复核（adjustment）** | Stop 时出现工具失败，或记录了关键歧义、重要调整；执行过 Plan 本身不触发 | 对照原目标与计划核对实际执行，是否换方法、跳过步骤或改变验证范围，调整是否影响原要求、是否需要披露 |
| **结果合理性审查（result）** | Stop 时执行过 Plan、调用／耗时达到阈值，或记录了结果限制；若也触发 adjustment，则在其后完成 | 实际执行与验证是否支持结论，结果比较、归因与声明范围是否合理，是否仍有重要限制 |

**触发要求：**

- **执行 Plan 前**：检查 `ambiguity`；普通 Prompt 不触发，无歧义则记录并继续。
- **结束时**：两类独立判断，满足任一项即触发对应阶段。`result`：当前 session 执行过 Plan、工具调用 ≥ **10 次**、执行耗时 ≥ **5 分钟**，或记录了结果限制。`adjustment`：出现工具失败，或记录了关键歧义、重要调整。执行过 Plan 强制触发 result，不强制触发 adjustment；无问题的 ambiguity 检查不算关键歧义。两类都触发时先 adjustment、后 result；均不满足则跳过。
- **执行中**：失败和验证结束只记录，不单独触发审查，结束前统一复核。

次数和时间为可配置默认值，按 session 累计；排除 Harness 调用、重复事件及等待用户、对话闲置的时间。失败沿用现有识别规则（工具错误标记或非零退出码）。检查完成后保留累计值及已审查范围；后续只核对新增或变化的相关内容，不因历史失败或已达阈值反复审查相同内容。

**两个触发信号**

- **`PostToolUse`（工具返回后）**：确定要执行 Plan 且尚未完成检查时，首次读取该 Plan 返回后提醒做 `ambiguity`；材料不足可继续读，检查完成后不重复提醒。Plan 已在上下文中时，确定执行便直接提醒，不等待读取。
- **`Stop`（准备结束本轮回答）**：优先检查是否等待用户澄清，是则放行提问，不触发结束审查；否则按当前 session 的累计条件分别选择 `adjustment`、`result`，两类都触发时先 adjustment、后 result。未完成则要求 Codex 继续检查。已完成且内容未变则复用。Stop 只表示本轮回答结束，不表示 session 结束，也不重置状态。

**检查类型与材料**

固定节点决定何时检查，以下类型决定具体审查内容：

| 类型 | 适用情况 | 默认材料 |
|---|---|---|
| `ambiguity` | 执行 Plan 前核对目标与计划是否存在关键歧义，不要求先发现问题 | 相关要求、Plan 上下文、拟采用的解释和澄清清单 |
| `adjustment` | 结束前核对执行过程相对原目标或计划的调整，不要求先记录重要调整 | 原要求、相关 Plan 步骤（如有）、执行与受阻记录、实际采取的方案及影响和调整复核清单 |
| `result` | 满足汇报前检查条件，包括成功、失败和部分完成 | 相关要求、拟汇报声明、执行与验证记录、过程中记录的事项和结果清单 |

**一个总 Skill、三个阶段 Skill**

各 Skill 应明确：**本 Harness 面向 autoresearch，即自动提出改进、修改代码、运行实验、比较基线并保留或回退的研究过程。审查目标是实验有效、比较公平、结论有依据，不能只检查代码能否运行。**

| Skill | 应写入的场景与检查问题 |
|---|---|
| `ebg-review` | 总入口：说明 autoresearch 场景、触发时机、阶段选择及 session 状态；统一要求数据隔离、实验可比、证据可追溯和结论不过度。明确必须取证、何时提问及如何披露。 |
| `ebg-ambiguity` | 实验前：优化目标和指标是什么？基线、数据版本与划分、训练／验证／测试集用途是否明确？哪些变量可改，哪些条件必须固定？资源预算、重复实验及保留／回退标准是否清楚？缺失项会影响比较或验收时，先核实再澄清。 |
| `ebg-adjustment` | 实验后复核过程：为什么换方案或回退，代码与失败记录是否支持该理由？是否换了数据、划分、预处理、指标、训练预算或评测方式？是否跳过验证、改用较小样本或代理任务？是否依据测试集结果调参或选模型？这些变化是否破坏原实验约束和可比性，是否需要重跑基线？ |
| `ebg-result-review` | 汇报前：训练数据或拟合预处理时是否混入测试数据？基线与候选是否在相同评测数据、指标及约定预算下比较？结果是否对应实际运行的代码、配置与模型？提升是否可能来自数据变化、额外算力、随机波动或挑选最佳运行？验证是否足以支持改进归因及保留／回退决定？ |

清单按“**检查问题 → 所需证据 → 对结论的影响**”编写。例如：训练集混入测试集，应追查数据加载、划分和预处理代码，不能将受污染的测试分数作为独立泛化证据；两次评测数据不同，不能直接把分数差归因于算法改进，应补做可比实验或限制结论。不要等模型自行意识到这些实验问题，也不要只写“检查结果是否合理”。具体标准依据任务的实验协议；数据变更若本身是研究变量，也须明确对照条件，不能默认任意差异都可直接比较。

总 Skill 保持简短，阶段内容按需加载。Hook 发出触发信号，总 Skill 说明流程，`ebg_review(trigger=...)` 返回对应阶段清单及共同规则，不要求模型自行猜选，也不一次加载全部阶段。现有 `ebg-disclose` 内容按此拆分；普通实现细节和已解决的普通报错不必单独审查或披露。

**需要用户澄清时**

发现关键歧义 → `ebg_evidence` 做必要核实 → `ebg_record` 记录待澄清 → Codex 提问并结束本轮回答 → 等用户答复。

- 取证只围绕该歧义。确认现有材料无法解决且需要用户选择后，立即说明歧义、影响及需要回答的问题，不必先审完整份 Plan，也不继续实施依赖该选择的方案。
- `ebg_record` 保存问题及受影响的决定，并返回明确提示：“现在向用户提出澄清问题，然后结束本轮回答，等待答复。”由 Codex 输出最终回复结束本轮；工具返回本身不是强制终止开关。
- 待澄清状态优先于结束审查：`Stop` 不返回 `block`，不要求先完成 `adjustment/result`，让询问正常结束；原有待审事项保留。
- 用户答复后，在同一 session 内更新要求；只有所需选择得到解决才清除待澄清状态，核对受影响部分后继续，不重置累计记录。

待澄清状态及 Stop 放行由代码实现；提问并结束回答由 Codex 按工具提示完成，工具返回本身不强制终止模型。

**取证、记录与披露**

1. `ebg_review` 返回相关 Prompt／Plan 原文、执行记录trace、拟作出的声明或决定及阶段清单，并冻结代码快照；不默认展开代码。已有适用检查点复用冻结材料。
2. **每项审查必须调用 `ebg_evidence`，不能等发现疑点才取证。** `ambiguity` 核实目标、Plan 及相关实现前提；`adjustment` 核实为什么调整或回退、实际改了什么；`result` 核实实现与验证是否支持结论。后两项必须查看相关代码及执行、验证证据，不能只凭 trace、总结、数字一致或命令成功下结论。
3. `ebg_evidence` 按审查问题展开同一检查点的代码、配置、数据来源及必要关联。材料不足则继续取证；缺少相关代码或实际验证时，补充材料、验证，或明确说明无法确认，不能判为 `clear`，也不能把检索当作实验。
4. `ebg_record` 保存判断、依据及处理情况。过程记录用 `note_kind="adjustment"` 表示重要调整、`"ambiguity"` 表示关键歧义、`"limitation"` 表示结果限制，进入对应阶段的触发判断。过程中重要调整应区分拟议／已执行、待确认／待披露；汇报前读取相关记录，不能仅保存而不复核。记录本身不代表已披露或获得授权。
5. 已有授权内的调整当时记录、继续执行，汇报时统一披露仍重要的影响。需要用户决定且已有授权未覆盖的取舍，在落实前说明问题、拟采取的行动和影响，等待答复后继续。关键前提未明确或决定仍待确认时，不能判为 `clear`。


**五个案例**

案例集包含一个 `ambiguity` 案例、一个 `adjustment` 案例和三个 `result` 案例。源码、Prompt 与运行方式见 [案例目录说明](../harness_case_study/README.md)。这些例子用于说明审查重点，不能据此估计稳定成功率。

**ambiguity：多个指标，没说清楚优化哪一个（设计案例）。** 任务要求改进分类器，Plan 写着“选择效果最好的配置”，评测同时输出准确率和召回率，却未说明优先优化哪个。两者可能出现取舍：一个方案准确率更高，另一个方案召回率更高。执行前应核对 Plan 和评分代码，确认没有既定规则后，询问用户以哪个指标为主、另一个有无最低要求；记录待澄清，等待答复后再确定优化方向，不能自行选择对结果更有利的指标。

**adjustment：并行失败后改串行，随机条件随入口变化（case2）。** 随机搜索基线与坐标细化候选在同一组问题、相同评估预算下比较。并行入口失败后，备用串行入口可以完成运行，却把基线的逐题独立 RNG 变为跨题共用 RNG；配置中的 seed 相同不代表实际随机条件相同。复核应比较原路径与替代路径的实现，识别对实验比较的影响，恢复可比条件或补做适当对照后再决定保留。仅披露“改用串行”不算识别该问题，也不能因存在差异就断言候选无效。新版 Skill 的一次试跑成功识别、修正并重跑，无问题对照未误报；这不代表稳定检出率。Prompt 和 Plan 不提示随机数一致性，当前案例保留待修复的初始状态。

**result：汇报前核对结果是否支持结论（历史案例）。**

1. **分数提高了，但训练数据混入了验证集。** 分类器从答对 86/120 提高到 90/120。审查追查新增训练样本的来源，发现其中 8 条由验证集派生；虽然编号不同，仍属于数据泄漏。最终披露问题并保留基线，没有采用受污染的结果。本轮未重跑过滤后的数据，因此不能断言合法的数据增强也无效。
2. **检查全通过，但没有真正调用 API。** 流水线完成优化后，验证显示 4/4 通过。审查发现实际使用的是模拟客户端，真实请求数为 0，原因是配置没有加载项目 `.env`。修复后重新验证，确认发出了真实请求并收到响应，才报告真实验证通过；性能结果仍只反映模拟工作负载下的调度开销。
3. **候选分数更高，但获得了更多调参机会。** 普通 SGD 只运行 1 次，准确率为 85.42%；动量 SGD 累计尝试 99 次，最佳为 89.58%。审查指出，更高分数可能同时来自优化器和更多调参投入。可以报告选中配置的分数更高，但没有等预算对照，不能把提升完全归因于优化器本身。
