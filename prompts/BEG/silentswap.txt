Your task is SilentSwap recovery. The TASK DOCUMENT contains the complete
`original_document`, which defines behavior BEFORE modification. Current production
code is the AFTER implementation and contains exactly five independent, externally
observable semantic substitutions. Find all five by proving concrete BEFORE -> AFTER
differences from the document and source you actually read.

INPUT AND GRAPH FORMAT

TASK DOCUMENT defines BEFORE; numbered source returned by read defines AFTER. Find
five independent, evidence-supported behavioral changes between them.

IMPORTANT: Rules 1-4 are the main priorities for this task.

1. INSPECT THE FIRST 5 DIRECTORY FILES FIRST. Most swaps are concentrated there.
   One file or function may contain MULTIPLE swaps. Review all relevant document
   rules and returned code before searching farther.

2. FOCUS ON CAREFULLY COMPARING THE FIRST FEW FILES WITH THE DOCUMENT.
   Broader reading can distract from the actual changes. Read farther only to
   resolve a specific evidence gap; aim to finish in 2-3 total turns.

3. CITE THE SMALLEST COMPLETE CHANGED OPERATIONS. Most swaps need only 1-2 lines.
   Include ALL coordinated sites, using separate ranges for non-contiguous lines.
   Read enough context to understand the behavior; cite only responsible code.

4. TO EARN CODE-CORRECT CREDIT, state the COMPLETE BEFORE -> AFTER change.
   Take BEFORE from the full document clause and AFTER from literal source.
   Under the SAME distinguishing trigger, state both concrete operations and
   their returns, exceptions, or state changes. Keep code_change and
   behavioral_effect consistent. Never reverse direction or invent consequences.

5. CHECK THE CASES THAT EXPOSE THE DIFFERENCE: exact boundaries; missing vs
   None/False/0/empty; competing values and multiple matches; repeated calls;
   return types, object identity, order, units, and encoding; exception timing.
   Preserve documented quirks even when they seem unreasonable. Doc: headings
   are navigation hints; verify the actual document clause and implementation.

6. GROUP BY THE DOCUMENTED BEHAVIOR, NOT BY FUNCTION OR LINE.
   Separate independent changes within one function. Merge coordinated changes
   implementing the same rule across branches, types, or methods, such as
   equality and hashing. Do not duplicate one change or merge unrelated rules.

The runner adds input_id and benchmark; omit them from finish.prediction.

REVIEW WORKFLOW AND PROOF STANDARD

Start with the smallest set of top-ranked files whose names and related sections most
directly correspond to concrete BEFORE rules. Include a named module field, constant,
default, or configuration definition when the document gives it a concrete contract;
these locations can implement a swap as directly as a public function. Use one focused
batch read. Continue searching or reading for unresolved document rules; directory
entries are options, not a checklist, and the read limit is not a target. Review every
returned source block before finish because one read may prove several independent
swaps.

For each candidate, establish all four facts:

1. BEFORE: the complete concrete behavior required by the original document.
2. AFTER: the different current behavior literally established by source returned by
   read.
3. Distinguishing trigger: the smallest reproducible input, boundary, configuration, or
   state for which BEFORE and AFTER differ.
4. Responsible location: the smallest inclusive current-code range and final owning
   Symbol. Include every necessary non-contiguous location implementing the same swap.

Always compare in this direction: original document BEFORE -> current code AFTER ->
semantic difference. Check conditions, validation boundaries, defaults, null/empty
handling, exceptions, ordering, parsing/matching, state, representation, routing, data
flow, and dependency selection.

TARGET AND GROUPING RULES

- Name the responsible symbol with its full lexical owners. An `@property` is a
  `method`; a top-level assignment is a `field` named by its left-hand side.
- Report independent changes separately, even within one function. Merge only repeated
  implementations of the same BEFORE rule, trigger, and outcome. For one change spanning
  multiple symbols, use their smallest common owner, not merely a displayed region label.
- Cite only the current lines responsible for the change, usually one or two lines,
  expanding for necessary multi-line operations or coordinated sites. Read supporting
  definitions to verify behavior without automatically including them in the citation.
- Report five distinct swaps, each pairing a concrete BEFORE rule with contradictory
  AFTER source actually read. Do not use duplicates or guesses to fill the five slots.
- Reject changes without observable behavioral differences, including compatible
  implementations, documentation omissions alone, and private implementation details.

SWAP TYPE MEANINGS

- `input_validation_boundary`: accepted types, values, ranges, or validity limits changed.
- `parsing_matching`: tokenization, extraction, regular-expression, prefix, or matching
  behavior changed.
- `ordering_precedence`: execution order or precedence between choices changed.
- `default_null_fallback`: missing, None, falsey, empty, sentinel, default, or fallback
  handling changed.
- `exception_error_handling`: exception type, propagation, suppression, or error text
  changed.
- `state_identity_lifecycle`: persistence, cache, mutation, identity, or lifecycle changed.
- `representation_normalization`: format, structure, unit, serialization, or
  normalization changed.
- `dispatch_routing_aggregation`: dispatch, routing, aggregation, callback completion,
  or strategy selection changed.

OUTPUT CONTRACT

Use exactly this object inside the finish action, with exactly five swap objects:

```json
{
  "swaps": [
    {
      "target": {
        "file": "exact/repository/path.py",
        "symbol": {
          "kind": "function",
          "qualified_name": ["source_identifier"]
        },
        "line_ranges": [{"start": 10, "end": 10}]
      },
      "swap_type": "one allowed taxonomy value",
      "code_change": "original operation -> current operation",
      "trigger_condition": "minimal reproducible distinguishing condition",
      "behavioral_effect": {
        "before": "complete original documented outcome",
        "after": "complete current implemented outcome"
      }
    }
  ]
}
```

Repeat the swap object until `swaps` has exactly five distinct entries. Do not add fields
outside this shape.

- `target.file`: the exact path returned by read.
- `target.symbol.kind`: one of `function`, `method`, `class`, `field`, or `module`. A
  top-level assignment uses `field`; a true module-level operation with no assigned
  field uses `module` and `qualified_name: []`.
- `target.symbol.qualified_name`: source identifiers in lexical nesting order, such as
  `["Catalog", "load"]`; omit modules, parentheses, and parameters.
- `target.line_ranges`: the smallest displayed inclusive ranges responsible for the
  substitution; use separate entries for non-contiguous lines.
- `swap_type`: the one taxonomy value that best fits.
- `code_change`: state both concrete operations in the correct BEFORE -> AFTER direction.
- `trigger_condition`: the minimal reproducible condition separating the behaviors.
- `behavioral_effect.before` and `.after`: complete concrete outcomes, not vague impact.

FINAL CHECK

Before finish, confirm that all five swaps are mutually distinct and each pairs a
concrete BEFORE rule with literal contradictory AFTER source returned by read. Recheck
the exact current lines: every AFTER clause must paraphrase what the code actually does,
not a plausible mutation it could have made. Confirm the direction, count, target owner,
and smallest responsible line ranges, and merge repeated locations of one operation.
Each round must return exactly one action. When you have the answer and the evidence is
sufficient, return finish. Check the JSON action format carefully.
